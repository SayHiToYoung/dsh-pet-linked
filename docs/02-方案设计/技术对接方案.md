# 小鲸 & 大鲸共享记忆技术对接方案

## 文档信息

- 产品代号：待定（小鲸 & 大鲸）
- 版本：v1.0 MVP
- 日期：2026-09-03
- 对接范围：共享记忆同步协议、服务端、桌面客户端、大鲸手机 PWA 与模拟接收端
- 输入依据：当前产品 MVP 描述与桌宠现有实现

## 一、技术概述

桌面小鲸负责低打扰采集，服务端只负责可靠保存、排序和交接，手机大鲸负责消费记忆与聊天。
本阶段用单用户、本地可部署的服务和可安装 PWA 验证闭环，不引入账号系统或推送服务。

技术目标：

- 同一条记忆重复上传不会重复入库或重复开场。
- 同一 ID 携带不同内容时拒绝写入，不能静默覆盖事实。
- 未收到服务端 ACK 的桌面批次永久保留在 outbox 中并退避重试。
- 大鲸开场以未消费的新记忆为输入；上一条助手消息未回复时不主动再发。
- 事实、推导、用户自述情绪继续保持 L1/L2/L3 来源边界。
- 远程服务必须使用 HTTPS；本机模拟器允许 `127.0.0.1` 明文 HTTP。

## 二、技术栈选择

- 桌面端：现有 Python 3 + PySide6；`urllib` 发送同步请求，不新增运行依赖。
- 服务端：Python 标准库 `ThreadingHTTPServer` + SQLite WAL。
- 模型层：复用桌宠现有 OpenAI Chat Completions 兼容配置；凭据只在服务端读取。
- 手机端：无框架 HTML/CSS/JavaScript PWA，由 Memory API 同源托管；支持离线外壳和回复 outbox。
- 大鲸模拟端：Python 命令行客户端，复用与手机端一致的 HTTP 协议。
- 原生客户端：验证通过后可使用 Flutter、React Native 或原生实现，不影响现有协议。

选择 SQLite 是因为当前只有设计者本人一个用户，重点是验证记忆连续性和情绪价值。协议与存储层分离，未来可将仓储实现替换为 PostgreSQL。

## 三、系统架构

```text
前台应用/窗口标题
        ↓
桌面 ActivityCollector → shared_memory.json → 幂等 outbox
                                           ↓ HTTPS/本机 HTTP
                                  Memory API → SQLite
                                           ↓ 原子 claim
                                  手机大鲸 PWA/命令行模拟器
                                           ↓ 用户回复
                                     conversation_messages
                                           ↓ 受约束上下文
                                  OpenAI 兼容模型 API
```

核心模块：

- `pet/activity_memory.py`：本地三层记忆与 outbox。
- `pet/memory_sync.py`：桌面顺序上传、指数退避和 ACK 落盘。
- `pet/memory_protocol.py`：协议校验、HTTP 客户端与事实型开场翻译。
- `pet/companion_llm.py`：记忆白名单、提示词、模型请求与事实防线。
- `pet/memory_server.py`：SQLite 仓储、API、消费游标和对话门禁。
- `mobile/`：大鲸手机 PWA、安装清单、离线缓存和消息 outbox。
- `scripts/run-memory-server.py`：本机服务模拟器。
- `scripts/run-big-whale-simulator.py`：大鲸接收端模拟器。

## 四、功能可行性评估

| 功能 | 难度 | 主要风险 | 当前处理 |
| --- | --- | --- | --- |
| 增量上传与 ACK | 中 | 响应丢失导致重复 | batchId 幂等，重复请求返回同一 ACK |
| 事实冲突保护 | 中 | 同 ID 被不同内容覆盖 | payload hash 不一致返回 HTTP 409 |
| 断线重试 | 中 | 服务不可用时刷请求 | outbox 保留，5 秒起指数退避，最高 5 分钟 |
| 大鲸自动开场 | 中 | 事实幻觉、重复发送 | 仅模板化使用存储字段；原子 claim + 对话门禁 |
| 大鲸模型回复 | 高 | 把推测写成事实或情绪 | 受约束提示词 + 白名单上下文 + 输出事实防线 + 本地兜底 |
| 手机断线恢复 | 中 | 用户回复丢失或重复 | localStorage outbox + messageId 幂等重试 |
| 最新状态承接 | 低 | 聚焦信息与最新信息混淆 | 开场聚焦持续最久项，同时返回 `latestMemory` |
| 多用户与正式鉴权 | 高 | 数据隔离与账号安全 | 不在 MVP；当前 Bearer 配对口令仅适合单用户验证 |

## 五、API 接口设计

基础路径为 `/v1`，请求头使用 `Authorization: Bearer <pairing-token>`。除 `/health` 外均需认证。

### 5.1 上传记忆批次

`POST /v1/memory/batches`

```json
{
  "protocolVersion": 1,
  "userId": "local-user",
  "deviceId": "desktop-xxx",
  "batchId": "report_xxx",
  "latestRevision": 12,
  "memories": [{
    "id": "fact_xxx",
    "revision": 12,
    "layer": "L1",
    "sourceType": "observed",
    "kind": "activity",
    "app": "Visual Studio Code",
    "durationSeconds": 3600
  }]
}
```

成功响应：

```json
{
  "accepted": true,
  "duplicate": false,
  "batchId": "report_xxx",
  "acceptedCount": 1,
  "latestServerSeq": 28,
  "receivedAt": "2026-09-03T10:00:00+00:00"
}
```

### 5.2 增量读取

`GET /v1/memory/stream?userId=local-user&afterServerSeq=0&limit=200`

响应包含 `memories`、`nextServerSeq` 和 `hasMore`。服务端序号只用于消费游标，不替代桌面端 revision。

### 5.3 原子领取大鲸开场

`POST /v1/companion/openings/claim`

```json
{
  "userId": "local-user",
  "deviceId": "phone-xxx",
  "claimId": "claim-xxx"
}
```

- 有新记忆且允许开场：`shouldSend=true`，返回稳定 `messageId`、`text`、`focusMemoryId`、`latestMemory` 和消费游标。
- 上一条助手消息未回复：`shouldSend=false, reason=awaiting_user_reply`。
- 没有新记忆：`shouldSend=false, reason=no_new_memory`。
- 同一 `claimId` 重试：返回原响应并标注 `duplicateClaim=true`。

### 5.4 写入对话消息

`POST /v1/conversation/messages`

```json
{
  "userId": "local-user",
  "deviceId": "phone-xxx",
  "messageId": "user-xxx",
  "role": "user",
  "text": "忙完了"
}
```

`messageId` 幂等；相同 ID、不同内容返回 409。
用户消息若含严格的第一人称明确情绪表达，服务端会同步生成一条 L3
`user_stated` 记忆；只陈述会议或工作事实时 `emotionRecorded=false`，不会猜测情绪。
成功响应还会返回 `assistantMessage` 和 `replySource`。用户消息先提交事务，再在数据库锁外调用
模型，避免模型超时堵塞同步；同一用户消息派生稳定回复 ID，重试只保存一条回复。

模型输入只包含最多 40 条白名单记忆与最近 20 条对话。系统提示明确约束 L1/L2/L3 来源；输出
若凭空定义用户情绪、增加无来源时长或断言项目已完成，会被事实防线拒绝并改用本地事实型回复。

### 5.5 读取对话历史

`GET /v1/conversation/messages?userId=local-user&afterMessageSeq=0&limit=200`

按 `messageSeq` 升序返回用户与大鲸消息。手机页启动时先恢复历史，再领取开场，避免把一次响应
丢失误判成尚未发送。

### 5.6 错误约定

- 400：字段、层级来源、revision 或请求体不合法。
- 401：配对口令错误。
- 404：接口不存在。
- 409：同一 batchId、memoryId 或 messageId 出现内容冲突。
- 500：服务端内部错误，不向客户端暴露数据库细节。

## 六、数据库设计

| 表 | 作用 | 关键约束 |
| --- | --- | --- |
| `memory_events` | 保存原始 L1/L2/L3 记忆 | `(user_id, memory_id)` 唯一 |
| `memory_batches` | 保存已确认批次 | `(user_id, batch_id)` 主键 |
| `conversation_messages` | 保存用户/大鲸消息顺序 | `(user_id, message_id)` 唯一 |
| `companion_cursors` | 每个大鲸设备的消费位置 | `(user_id, device_id)` 主键 |
| `opening_claims` | 保存开场领取响应 | `(user_id, device_id, claim_id)` 主键 |

SQLite 使用事务和 `BEGIN IMMEDIATE` 保证开场领取、消息创建、游标推进不可被并发请求拆开。

## 七、第三方服务

大鲸对话会调用用户在桌宠 AI 设置中选择的 OpenAI 兼容模型服务，成本遵循该服务商定价；未配置
凭据或请求失败时不产生模型费用，自动使用本地事实型回复。PWA 使用仓库内现有鲸鱼插画，不依赖
外部 CDN。未来公网部署还需要 HTTPS 证书、托管数据库和备份。

## 八、非功能性要求

- 最大请求体 512KB；每批最多 20 条；单条记忆最多 16KB。
- 桌面默认每 30 秒检查一次 outbox；失败采用最高 5 分钟退避。
- 远程 URL 禁止明文 HTTP。
- 服务端不修改客户端事实，只附加 `serverSeq/sourceDeviceId/receivedAt`。
- API Key 只由服务端从系统钥匙串或环境变量读取，不下发到手机，也不写入对话数据库。
- 模型请求最长等待 30 秒；请求期间不持有 SQLite 写锁。
- 当前配对口令保存在本机配置，适合个人验证，不视为正式账号安全方案。
- SQLite 文件应纳入加密备份；公网部署前必须补充用户认证、密钥轮换、删除与导出能力。

## 九、部署方案

本机验证：桌宠、Memory API 和大鲸 PWA 在同一台电脑运行，浏览器访问
`http://127.0.0.1:47821/`。实体手机验证需要把同一服务放到 HTTPS 反向代理之后；手机只配置
HTTPS 地址与配对凭证，再从浏览器添加到主屏幕。

本阶段不包含容器、CI/CD 或公网发布，避免在情绪价值尚未验证前增加运维成本。

## 十、风险与应对

- 窗口标题可能含敏感文字：默认仅用户主动开启同步后上传；未来增加字段级脱敏。
- LLM 仍可能尝试越过事实边界：高风险断言由服务端拦截；无法证明安全时使用本地回复，不把模型
  输出直接写成 L1/L2/L3 记忆。
- 多设备同时领取：当前每设备有独立游标，但对话门禁按同一用户共享，避免两个大鲸同时主动说话。
- 响应丢失：同 claimId 可恢复原开场；新 claimId 可取得待显示的上一条助手消息。

## 十一、后续排期建议

1. 当前：本机跑通桌宠 → 服务 → 受约束模型 → 大鲸手机 PWA → L3 回写闭环。
2. 下一步：部署个人 HTTPS 服务，在实体手机连续使用一周，记录 7 次开场是否真实、是否重复、
   是否“心里软了一下”。
3. 验证通过后：增加设备配对页、账号与备份，再评估原生客户端。
4. 最后：根据一周使用结果迭代人设与追问策略，保留事实防线和本地兜底。
